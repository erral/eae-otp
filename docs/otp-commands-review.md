**Review date:** 2026-11-25
**Scope:** steps 1–3 of the “Instalatu” section of [`README.md`](../README.md), plus the
`build-config.json` / `router-config.json` generated by `download_and_process.py`.
**Method:** official OTP documentation, OTP source code at the `v2.10.0` tag and on
`dev-2.x`, the Docker Hub registry API, the GitHub releases feed, and direct tests with
Docker on this machine.

| README item | Verdict | Short reason |
| --- | --- | --- |
| `python download_and_process.py` | **Correct, with a portability caveat** | The script is Python 3-only. `python` may not exist on current Linux distributions; `python3` is safer. |
| Build command (`--build --save`) | **Correct** | Copied verbatim from the official container quick-start. `--save` is required to write `graph.obj`. |

| `JAVA_TOOL_OPTIONS='-Xmx8g'` | **Correct** | Documented by OTP; honoured by the JVM. `JAVA_OPTS` also works in this image. |

## 2. Image name and working directory

**[Docs]** The official Container Image page says:

> The image assumes you use a volume to mount the input data (GTFS/NeTEx, OSM) and config
> files into `/var/opentripplanner/`. When serving a graph it's also expected to be in this
> directory.

The same page’s quick-start uses exactly:

```bash
docker.io/opentripplanner/opentripplanner:latest
```

and mounts `"$(pwd)/berlin:/var/opentripplanner"`.

**[Source]** The image is built with Jib. `container/pom.xml` on `dev-2.x` declares a volume
`/var/opentripplanner/` and exposes ports 8080 and 8081. The entrypoint is:

```bash
java $JAVA_OPTS -cp @/app/jib-classpath-file @/app/jib-main-class-file /var/opentripplanner/ $@
```

`/var/opentripplanner/` is therefore passed to OTP as the *base directory* (the positional
argument), which is where OTP looks for `build-config.json`, `router-config.json`, GTFS,
OSM and `graph.obj`. The 2.10.0 image uses the same entrypoint from
`application/src/main/jib/docker-entrypoint.sh`.

**[Observed]** The serve command was run with
`-v "$(pwd)/eae:/var/opentripplanner"`. OTP read `/var/opentripplanner/graph.obj` and served
HTTP 200. The build command was not re-run (an existing graph was already present), but the
build artifact lives in the same mounted directory and is the file OTP loads. The mount path
is correct for both phases.

**Verdict: correct.** Note that `docker.io/` is optional (Docker Hub is the default
registry), but it is also what the official docs use, so there is no reason to change it.

## 3. CLI flags: `--build --save` and `--load --serve`

### 3.1 What the official docs say

**[Docs]** The Basic Tutorial (2.10.0) states:

- Required parameters are `--load`, `--loadStreet`, `--build`, or `--buildStreet`.
- “`--load` implies `--serve`, so `--serve` is not necessary and has no additional effect
  when used together with `--load`.”
- `--build --save` “will produce a file called `graph.obj` in the same directory as the
  inputs.”
- `--load` reads `graph.obj` instead of building from scratch.

The Container Image page uses the two README commands verbatim, including
`--build --save` and `--load --serve`.

### 3.2 What the source code says

**[Source]** `application/src/main/java/org/opentripplanner/standalone/config/CommandLineParameters.java`
(2.11.0-SNAPSHOT; same logic in 2.10.0) enforces:

- Exactly one of `--load`, `--build`, `--loadStreet`, `--buildStreet` must be given.
- `--build` and `--loadStreet` must be combined with `--save` or `--serve` (or both).
- `--load` cannot be combined with `--save`.
- `doServe()` returns `load || (serve && doBuildTransit())`.

Consequences:

- `--build --save` without `--serve` is valid, does **not** start the server, and writes
  `graph.obj`. The `--save` flag is what causes `graph.obj` to be written.
- `--build` alone (neither `--save` nor `--serve`) is rejected.
- `--load` alone is enough to load and serve; `--serve` is redundant.
- `--serve` alone is **not** enough: it produces `Parameter error: Nothing to do.`

### 3.3 Empirical checks

**[Observed]** Against `opentripplanner/opentripplanner:latest`:

| Command | Result |
| --- | --- |
| `--build --save` | Not re-run here. The existing `eae/graph.obj` (220.7 MB, generated 2026-11-25 with the 2.11 snapshot) proves the input set builds with this image and that `--save` produced the artifact. |
| `--load --serve` | HTTP 200 on port 8080 after ~9 s. |
| `--load` (without `--serve`) | `Grizzly server running`, HTTP 200 after ~9 s. |
| `--serve` (alone) | `ERROR ... Parameter error: Nothing to do. Use --help to see available options.` |

**[Observed]** `--help` confirms the semantics in its own descriptions:

```
--load
  Load 'graph.obj' and serve it. The '--serve' parameter is implied.
--save
  Save the 'graph.obj' ...
--port
  Server port for plain HTTP.
  Default: 8080
```

### 3.4 Did the CLI change in 2.5–2.10?

**[Docs]** The docker invocations and OTP flags are identical in the official container
docs for **v2.6.0, v2.8.1, v2.9.0 and v2.10.0** (v2.5.0 has no `Container-Image.md` at that
path). v2.6.0 omits the `-e JAVA_TOOL_OPTIONS=...` lines, but the `--build --save` and
`--load --serve` invocations are unchanged. The v2.8.1 source has the same
“`--build` must be used with `--save` or `--serve`” validation.

**[Inference]** For the flag combinations used in this README, there is no relevant CLI
change between 2.5 and 2.11. The only semantic nuance is that `--serve` has always needed a
build/load action behind it; `--load` is the action here, and it implies `--serve`.

**Verdict: both commands are correct.** `--load --serve` can stay (it matches the official
docs); dropping `--serve` is equally correct and slightly clearer about what `--load` does.

## 4. JVM heap: `JAVA_TOOL_OPTIONS` vs `JAVA_OPTS`

**[Docs]** The Container Image page explicitly recommends:

> If you want to set JVM options you can use the environment variable `JAVA_TOOL_OPTIONS`,
> so a full example to add to your docker command is `-e JAVA_TOOL_OPTIONS='-Xmx4g'`.

**[Source]** The image entrypoint expands `$JAVA_OPTS` explicitly:

```bash
java $JAVA_OPTS -cp ... /var/opentripplanner/ $@
```

So the image supports **both**:

- `JAVA_TOOL_OPTIONS` — a standard JVM variable; the JVM picks it up automatically and
  prints `Picked up JAVA_TOOL_OPTIONS: ...`.
- `JAVA_OPTS` — expanded by the entrypoint script itself.

**[Observed]** Both were tested:

```
$ docker run --rm --entrypoint java -e JAVA_TOOL_OPTIONS='-Xmx8g' <image> -XshowSettings:vm -version
Picked up JAVA_TOOL_OPTIONS: -Xmx8g
    Max. Heap Size (Estimated): 8.00G

$ docker run --rm -e JAVA_OPTS='-Xmx3g -XshowSettings:vm' <image> --version
    Max. Heap Size: 3.00G
```

**Verdict: `JAVA_TOOL_OPTIONS` is correct** and is the documented choice. It does apply the
heap limit as intended. `JAVA_OPTS` is an alternative that also works in this image, but
there is no need to change the README. One minor consequence of `JAVA_TOOL_OPTIONS` is that
its value is echoed to stderr at startup and applies to any JVM started in the container.

## 5. Port and `-it`

**[Docs]** The Basic Tutorial: “OTP’s built-in web server will run by default on port 8080.”
A different port can be selected with `--port`.

**[Source]** `CommandLineParameters.DEFAULT_PORT = 8080`; the Jib build declares port 8080
(and 8081) in the image.

**[Observed]** `-p 8080:8080` (and `-p 18080:8080` in tests) work; the server answers on the
mapped host port.

`-it` is **not required** to serve. It only allocates an interactive terminal so that
Ctrl+C works and log output is attached. The container served normally in detached mode
(`docker run -d`, no `-it`). In non-interactive contexts (CI, scripts), `-it` can fail with
`the input device is not a TTY`, so it is better omitted there.

**Verdict: `-p 8080:8080` is correct; `-it` is optional.** Security note: `-p 8080:8080`
publishes on all host interfaces. For a local-only service use
`-p 127.0.0.1:8080:8080`.

## 6. Is `latest` safe, and does the config schema match?

### 6.1 What `latest` currently resolves to

**[Observed]** Docker Hub’s registry API on 2026-11-25 reports:

| Tag | Digest | Last updated |
| --- | --- | --- |
| `latest` | `sha256:39776f292c713e0b2b6087f35c8f3c3970863027ae28a926bbd39ed54e4a6ecc` | 2026-11-25 14:01 UTC |
| `2.11.0_2026-11-25T14-00` | `sha256:39776f292c713e0b2b6087f35c8f3c3970863027ae28a926bbd39ed54e4a6ecc` | 2026-11-25 14:01 UTC |
| `2.10.0` | `sha256:8d54e5c589186707ee365417f2202dc878c451fa3001b8edff07019531100933` | 2026-09-09 09:23 UTC |

`latest` and the `2.11.0_<timestamp>` snapshot build have the **same digest**. Running the
image confirms `OpenTripPlanner Version: 2.11.0-SNAPSHOT`. The latest GitHub release at
this date is **v2.10.0 (September 2026)**; there is no 2.11.0 release yet.

**[Inference]** On 2026-11-25, `latest` is a **moving development snapshot**, rebuilt
frequently (several tagged builds per day), not the stable release. That is also what the
official docs point at, so the README is consistent with the docs — but it means every
`docker run` can silently use a different OTP build.

### 6.2 Why that is risky in practice

**[Observed]** The existing `eae/graph.obj` was built with the 2.11.0-SNAPSHOT image
(serialization id 292). Trying to serve it with the stable 2.10.0 image fails:

```
The graph file is incompatible with this version of OTP. The OTP serialization version id
'277' do not match the id '292' in '/var/opentripplanner/graph.obj' file-header.
```

`--load` therefore couples the graph file to the exact OTP serialization version. If the
`latest` tag moves to a build with a new serialization id, the previously built graph can no
longer be served until it is rebuilt — which is exactly the kind of failure a `latest`-based
README can produce.

### 6.3 Config schema compatibility

**[Observed]** Serving the repo’s configs with the 2.11.0-SNAPSHOT image produced **66
warnings**, all of the same kind:

```
WARN (NodeAdapter.java:168) Unexpected config parameter: 'updaters.[0].frequencySec:30' in 'router-config.json'
```

No other parameter produced a warning. The existing graph also shows that the build
configuration was accepted when it was built.

| Config key | 2.10.0 | 2.11.0-SNAPSHOT | Basis |
| --- | --- | --- | --- |
| `build-config.json` → `osmDefaults` (`osmTagMapping`, `timeZone`) | valid | valid | [Docs] Build Configuration; unchanged on `dev-2.x` |
| `build-config.json` → `transitModelTimeZone` | valid | valid | [Docs] Build Configuration; since 2.2 |
| `build-config.json` → `transitFeeds[]` (`type: gtfs`, `source`, `feedId`) | valid | valid | [Docs] Build Configuration; graph built successfully |
| `router-config.json` → `updaters[].type`: `real-time-alerts`, `stop-time-updater`, `vehicle-positions` | valid | valid | [Docs] GTFS-RT Config; no warnings for these keys |
| `router-config.json` → `updaters[].backwardsDelayPropagationType` (`REQUIRED_NO_DATA`) | valid | valid | [Docs] since 2.2, default `required-no-data`; uppercase form accepted (no warning; docs example uses uppercase) |
| `router-config.json` → `updaters[].frequencySec` | **invalid** | **invalid** | [Observed] 66 warnings; [Source] config classes only read `frequency` |
| `router-config.json` → `updaters[].frequency` (ISO-8601 duration, e.g. `"30s"`) | valid | valid | [Docs] GTFS-RT Config, since 1.5, default `PT1M` |

**[Source]** In `VehiclePositionsUpdaterConfig.java`, `PollingTripUpdaterConfig.java` and
`GtfsRealtimeAlertsUpdaterConfig.java` (v2.10.0 and `dev-2.x`), the only polling key is
`frequency`, parsed as a `Duration` with a default of one minute. A grep for `frequencySec`
in the vehicle-positions updater config returns zero hits in v2.5.0, v2.6.0, v2.7.0, v2.8.1,
v2.9.0, v2.10.0 and `dev-2.x`: this is **not** an OTP 2.x key and has not been for the
versions reviewed.

**[Inference]** Because unknown keys are ignored (the default behaviour; see the official
migration guide), the practical effect is:

- `real-time-alerts` intended 30 s → actually polled every 60 s (the default).
- `stop-time-updater` intended 60 s → unchanged (default is 60 s).
- `vehicle-positions` intended 60 s → unchanged (default is 60 s).

So the bug is mostly harmless today, but it is a real configuration error and would matter
if a non-default polling interval were intended. The correct fix (in
`download_and_process.py`, not done here because this review is read-only) is to emit
`"frequency": "30s"` / `"frequency": "60s"` instead of `"frequencySec": 30` / `: 60`.

### 6.4 Recommendation

Pin an exact version in **both** commands, and use the same version for build and serve.
The latest stable release at the review date is `2.10.0`:

```bash
docker.io/opentripplanner/opentripplanner:2.10.0
```

or, stronger, the multi-arch manifest digest:

```bash
docker.io/opentripplanner/opentripplanner@sha256:8d54e5c589186707ee365417f2202dc878c451fa3001b8edff07019531100933
```

**Important:** if you pin `2.10.0`, rebuild `graph.obj`. The current graph was built with
the 2.11.0-SNAPSHOT image (serialization id 292) and cannot be loaded by 2.10.0 (id 277).
Pinning also means that an OTP upgrade becomes a deliberate act (rebuild graph, re-test)
rather than a side effect of `docker run`.

## 7. Additional flags and memory sizing

### 7.1 Are extra flags needed?

**[Inference]** No additional flags are required for this dataset:

- `--save` is already present, so `graph.obj` is written into `eae/`.
- The default base directory is supplied by the image entrypoint; the README does not need
  to repeat `/var/opentripplanner`.
- The default HTTP port (8080) is used.
- The build config explicitly lists all 36 GTFS feeds, so filename-based GTFS detection is
  not relied upon (although every file also contains “gtfs” in its name, which satisfies
  OTP’s convention).
- OSM files are auto-detected by the `.pbf` extension; both regional extracts are loaded.

Optional hardening: add `--abortOnUnknownConfig` to the serve command to make unknown
configuration parameters fatal. That would have turned the 66 `frequencySec` warnings into
an immediate startup failure, which is useful in CI.

### 7.2 Is `-Xmx8g` plausible?

Measured inputs in `eae/` at review time:

| Item | Value |
| --- | --- |
| GTFS feeds | 36 |
| Total GTFS zip size | 69.5 MB |
| Total `stop_times.txt` rows | 4,210,909 (largest feed: 1,829,967 — Renfe Cercanías) |
| OSM PBF size | 107.2 MB (Basque Country + Navarra) |
| Resulting `graph.obj` | 220.7 MB |

**[Docs]** The official System Requirements page says OTP memory use ranges “from less than
one GB to more than 100 GB”, giving Finland at a bit over 10 GB and Germany at 95 GB as
examples.

**[Observed]** The 220.7 MB graph loads and serves in about 9 seconds with `-Xmx8g`.

**[Inference]** 8 GB is plausible and comfortable for this dataset, which is much smaller
than the Finland or Germany examples. It may well build with 4 GB, but 8 GB is a safe,
documented default and matches the official quick-start. Two caveats:

- The 8 GB is the Java **heap** limit; the host needs more than 8 GB free for the JVM,
  container overhead and the OS. The README sets no Docker memory limit, so an
  under-provisioned host will be killed by the OOM killer.
- The graph was already present when this review started; I did not re-run the full build
  (that would have overwritten the existing artifact, and the host had only ~3 GB free at
  the time). The existence of a valid 220.7 MB `graph.obj` and its successful load are the
  direct evidence that the build pipeline works, but the exact peak build memory was not
  measured here.

OTP 2.8.0 explicitly reduced graph-build memory consumption (PRs #6724, #6752), and 2.10.0
included further build-performance work, so 8 GB is more conservative on current versions
than it would have been on older ones.

## 8. Other README issues and edge cases

1. **`python` vs `python3`.** `download_and_process.py` uses f-strings, `pathlib` and
   `urllib`, i.e. Python 3.6+. Many current distributions (including Ubuntu 24.04) do not
   provide a `python` executable by default. The README’s `python download_and_process.py`
   will fail there with `command not found`. Prefer `python3`.
2. **Working directory.** `"$(pwd)/eae"` is correct **only if the command is run from the
   repository root**. Running it from inside `eae/` produces `eae/eae`. The quoting itself
   is correct and handles paths with spaces. A note such as “run from the repository root”
   or an absolute path would remove the ambiguity.
3. **`-p 8080:8080` exposes the service on all host interfaces.** Fine for a development
   machine; use `-p 127.0.0.1:8080:8080` if it should only be reachable locally.
4. **`-it` is unnecessary for serving** and breaks non-TTY contexts. It is harmless in an
   interactive terminal.
5. **`graph.obj` is written as `root`.** The container runs as root by default, so
   `eae/graph.obj` is owned by `root` on the host. It does not prevent rebuilding (the
   directory is writable by the owner), but it is surprising. Adding
   `--user "$(id -u):$(id -g)"` is an option if the mounted directory is writable by that
   user.
6. **No missing `--rm`.** Both commands already include it.
7. **No wrong volume or working directory.** `/var/opentripplanner` is correct for both the
   input/build phase and the serving phase.
8. **Real-time updaters need outbound network access.** The router config defines 66
   updaters pointing at `opendata.euskadi.eus`. If the container has no outbound access,
   the server still starts but the updaters log fetch failures; that is expected and not a
   command error.
9. **Build/serve asymmetry with `latest`.** If the README keeps `latest`, the build and
   serve commands should be run close together, and the graph should be rebuilt whenever
   the tag changes to a new serialization version. Pinning avoids the whole class of
   problem.

## 9. Corrected commands

The commands below are the README commands with the three recommended changes: Python 3
explicitly, OTP pinned to the stable release, and `--serve` dropped because `--load`
implies it. (Keeping `--load --serve` is also correct.)

```bash
# 1. Download, validate and configure
python3 download_and_process.py

# 2. Build the graph and save graph.obj into ./eae
docker run --rm \
  -e JAVA_TOOL_OPTIONS='-Xmx8g' \
  -v "$(pwd)/eae:/var/opentripplanner" \
  docker.io/opentripplanner/opentripplanner:2.10.0 --build --save

# 3. Load and serve on http://localhost:8080
docker run --rm -p 127.0.0.1:8080:8080 \
  -e JAVA_TOOL_OPTIONS='-Xmx8g' \
  -v "$(pwd)/eae:/var/opentripplanner" \
  docker.io/opentripplanner/opentripplanner:2.10.0 --load
```

If the README keeps `:latest`, at minimum add a note that `latest` is a development
snapshot, that build and serve must use the same tag, and that the graph must be rebuilt
after an OTP upgrade. Also fix the generated router config (`frequencySec` → `frequency`).
